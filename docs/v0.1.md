## 1. O projeto e o objetivo da v0.1

O **Busca Fácil** é uma plataforma de **busca e comparação de preços** de produtos entre lojas. É um projeto de estudo, feito para aplicar na prática desenvolvimento web, APIs REST, bancos de dados e arquitetura de sistemas.

O projeto é construído em **versões incrementais**, cada uma acrescentando entidades ao modelo de dados (`modelo-dados.md`):

| Versão | Entidades | O que permite |
|---|---|---|
| **v0.1** ✅ | **Produto** | **Cadastrar e pesquisar produtos** |
| v0.2 | Loja, Oferta | Registrar preços de cada produto em cada loja; comparar preços |
| v0.3 | Usuario | Cadastro e login de usuários |
| v0.4 | Favorito | Usuários guardarem produtos favoritos |

**Objetivo da v0.1:** construir a **base técnica completa** (projeto Spring Boot, banco, Docker, camadas, testes, tratamento de erros) com a entidade mais simples, Produto. As próximas versões reaproveitam essa estrutura e só acrescentam entidades.

## 2. Funcionalidades

### O que a v0.1 faz

| Funcionalidade | Como usar | Detalhe |
|---|---|---|
| **Cadastrar produto** | `POST /produtos` | Nome obrigatório (até 150 caracteres); descrição (até 1000) e categoria (até 80) opcionais |
| **Listar produtos** | `GET /produtos` | Devolve todos; lista vazia `[]` se não houver nenhum |
| **Pesquisar por nome** | `GET /produtos?nome=note` | Encontra o texto em qualquer posição do nome, sem diferenciar maiúsculas de minúsculas |
| **Consultar um produto** | `GET /produtos/{id}` | `404` se não existir |
| **Alterar produto** | `PUT /produtos/{id}` | Substitui nome, descrição e categoria |
| **Remover produto** | `DELETE /produtos/{id}` | `204` em caso de sucesso; `404` se não existir |

### Comportamentos garantidos (regras de negócio)

- **Nome obrigatório**: vazio, só espaços ou ausente é recusado com `400` e uma mensagem por campo.
- **Limpeza de texto**: espaços nas pontas são removidos (`"  Notebook  "` → `"Notebook"`), e campos opcionais em branco viram vazio (`null`).
- **Proteção do id**: o `id` é sempre gerado pelo banco. Um `id` enviado pelo cliente é ignorado, e ninguém consegue sobrescrever outro produto pela rota de criação.
- **Erros padronizados**: todo erro vem no mesmo formato JSON (Problem Details), com título, status e explicação.
- **Dados persistentes**: os produtos ficam no MySQL e sobrevivem a reinícios dos containers.

### O que ainda não faz

Lojas, ofertas e preços (v0.2), usuários (v0.3), favoritos (v0.4), paginação da listagem, autenticação e front-end.

## 3. Tecnologias e por que cada uma

### Visão geral

| Camada | Tecnologia | Versão |
|---|---|---|
| Linguagem | Java | 25 |
| Framework | Spring Boot | 4.1.1 |
| Web | Spring Web MVC + Tomcat (embutido) | Tomcat 11 |
| JSON | Jackson | 3.1 |
| Persistência | Spring Data JPA + Hibernate | Hibernate 7.4 |
| Validação | Bean Validation (Hibernate Validator) | - |
| Redução de código repetitivo | Lombok | - |
| Banco de dados | MySQL | 8.0 |
| Banco dos testes | H2 (em memória) | 2.4 |
| Build | Maven (via Maven Wrapper) | 3.9 |
| Testes | JUnit 5, Mockito, AssertJ, MockMvc | Mockito 5.23 |
| Containers | Docker + Docker Compose | - |

### Por que cada escolha

#### Java 25
**O que é:** linguagem de programação orientada a objetos, compilada para *bytecode* e executada pela **JVM** (*Java Virtual Machine*), o que permite rodar o mesmo programa em qualquer sistema operacional.
**Por que usar:** é uma das linguagens mais usadas em back-end corporativo, tem tipagem forte (muitos erros aparecem já na compilação) e um ecossistema enorme. A versão 25 é a mais recente com suporte de longo prazo (**LTS**) e traz recursos modernos usados no projeto, como os `record`s dos DTOs e os *text blocks* (`"""`) dos testes.

#### Spring Boot 4.1
**O que é:** um framework, ou seja, uma base pronta sobre a qual a aplicação é construída. O **Spring** oferece injeção de dependência, web, acesso a dados, transações e muito mais. O **Spring Boot** adiciona **configuração automática**: detecta as bibliotecas no projeto e configura tudo com padrões sensatos.
**Por que usar:** é o framework Java mais usado para APIs. Com ele, a aplicação inteira inicia com uma classe de 10 linhas (`BackendApplication`). Os **starters** (`spring-boot-starter-webmvc`, `-data-jpa`, `-validation`) trazem cada recurso com versões compatíveis entre si.
**Alternativas:** Quarkus e Micronaut (mais leves, menos material de estudo), Jakarta EE puro (mais configuração manual).

#### Spring Web MVC + Tomcat
**O que é:** o **Spring MVC** faz o roteamento das requisições HTTP para os métodos Java (`@GetMapping`, `@PostMapping`...). O **Tomcat** é o servidor web que recebe as conexões na porta 8080. Ele vem **embutido** no `.jar`.
**Por que usar:** é o modelo web padrão e mais documentado do Spring. Com o servidor embutido, basta `java -jar app.jar` para ter a API no ar, sem instalar servidor à parte.

#### Jackson
**O que é:** a biblioteca que converte objetos Java em JSON e vice-versa.
**Por que usar:** vem configurada pelo Spring Boot. O controller recebe e devolve objetos Java comuns, e o Jackson faz a tradução automaticamente.

#### Spring Data JPA + Hibernate
**O que é:** **JPA** é a especificação Java para **ORM**, o mapeamento de classes para tabelas. O **Hibernate** é a implementação que gera e executa o SQL. O **Spring Data JPA** cria os repositories automaticamente a partir de interfaces.
**Por que usar:** elimina o SQL repetitivo. O `ProdutoRepository` tem **uma linha de código útil** e ganha `save`, `findAll`, `findById`, `deleteById` e uma busca por nome gerada a partir do nome do método. O Hibernate também cria as tabelas a partir das classes e gera o SQL no **dialeto** certo para cada banco (MySQL ou H2).
**Alternativas:** JDBC puro ou Spring JDBC (SQL manual, mais controle e mais código), jOOQ (SQL tipado), MyBatis.

#### Bean Validation
**O que é:** uma especificação para declarar regras de validação com anotações (`@NotBlank`, `@Size`).
**Por que usar:** as regras ficam **declaradas** no DTO, legíveis num relance, e o Spring as aplica automaticamente com `@Valid`. Dados inválidos são recusados antes de chegar à lógica da aplicação.

#### Lombok
**O que é:** um processador de anotações que **gera código durante a compilação**: getters, setters, construtores.
**Por que usar:** a entidade `Produto` fica com 26 linhas em vez de cerca de 70. Usamos só `@Getter`, `@Setter` e `@NoArgsConstructor`, e evitamos o `@Data`, que causa problemas em entidades JPA (`entidade-produto.md`, seção 3).

#### MySQL 8
**O que é:** um dos bancos de dados relacionais mais populares do mundo, gratuito e de código aberto.
**Por que usar:** relacional combina com o modelo do projeto (produtos, lojas, ofertas e as **relações** entre eles). É amplamente usado em hospedagens e no mercado e tem imagem oficial no Docker.
**Observação:** o README original citava PostgreSQL, mas a implementação adotou MySQL. Os dois serviriam bem; a troca exigiria apenas outro driver e outra URL, graças à JPA.

#### H2 (só nos testes)
**O que é:** um banco SQL escrito em Java que roda **dentro da memória** da aplicação.
**Por que usar:** os testes rodam em qualquer máquina, em segundos, **sem Docker e sem MySQL**. Cada execução começa com um banco limpo. Entra no projeto com `scope test`, então não vai para o `.jar` final.
**Limitação:** imita o MySQL (`MODE=MySQL`), mas não é idêntico. Recursos muito específicos do MySQL exigiriam **Testcontainers**.

#### Maven + Maven Wrapper
**O que é:** o **Maven** gerencia o projeto Java: baixa as dependências declaradas no `pom.xml`, compila, roda os testes e gera o `.jar`. O **Wrapper** (`mvnw`, `mvnw.cmd`) é um script que baixa a versão certa do Maven automaticamente.
**Por que usar:** é o padrão dos projetos Spring. Com o Wrapper, qualquer pessoa compila o projeto sem instalar o Maven, e todos usam a mesma versão.
**Alternativa:** Gradle (mais flexível e rápido, configuração em código).

#### JUnit 5, Mockito, AssertJ e MockMvc
**O que são:**
- **JUnit 5**: o executor de testes (`@Test`).
- **Mockito**: cria **mocks**, objetos falsos que substituem dependências.
- **AssertJ**: verificações legíveis (`assertThat(x).isEqualTo(y)`).
- **MockMvc**: simula requisições HTTP sem abrir servidor.

**Por que usar:** é o conjunto padrão no ecossistema Spring, e todos vêm nos starters de teste. Permitem testar cada camada isoladamente e rápido.

#### Docker + Docker Compose
**O que é:** o **Docker** executa aplicações em **containers**, ambientes isolados e reproduzíveis. O **Compose** sobe vários containers juntos a partir de um arquivo YAML.
**Por que usar:**
- O MySQL roda **sem ser instalado** no Windows.
- O ambiente é **igual em qualquer máquina**: um `docker compose up` e tudo funciona.
- O banco e a API sobem **na ordem certa**, graças ao healthcheck.
- A imagem do back-end é a mesma que iria para um servidor.

## 4. Arquitetura

### Visão do sistema

```
┌─────────────┐      HTTP/JSON       ┌──────────────────────┐       JDBC        ┌──────────────┐
│  Cliente    │ ───────────────────► │  Back-end            │ ────────────────► │  MySQL 8     │
│ (curl,      │ ◄─────────────────── │  Spring Boot         │ ◄──────────────── │  busca_facil │
│  navegador) │     porta 8080       │  container Docker    │    porta 3306     │  container   │
└─────────────┘                      └──────────────────────┘                   └──────────────┘
```

### Camadas do back-end

```
HTTP ──► Controller ──► Service ──► Repository ──► Entidade ──► MySQL
         (HTTP⇄Java)    (regras)    (dados)        (tabela)
                 ╲
                  TratadorDeErros: exceções → respostas HTTP padronizadas
```

Cada camada tem **uma responsabilidade** e só conversa com a vizinha de baixo:

| Camada | Pergunta que responde |
|---|---|
| **Controller** | Quais URLs existem, e qual o formato do JSON e do status? |
| **Service** | Isso é permitido? (regras de negócio) |
| **Repository** | Como salvar e buscar no banco? |
| **Entidade** | Como o dado é guardado (tabela e colunas)? |

**Por que separar assim:** cada mudança tem um lugar óbvio, as regras valem para qualquer porta de entrada e cada camada pode ser testada isoladamente.

### Organização do código: por funcionalidade

```
backend/src/main/java/com/busca_facil/backend/
├── BackendApplication.java     ponto de entrada
├── erro/                       compartilhado por todas as funcionalidades
│   └── TratadorDeErros.java
└── produto/                    tudo sobre Produto, junto
    ├── Produto.java
    ├── ProdutoRepository.java
    ├── ProdutoService.java
    ├── ProdutoNaoEncontradoException.java
    ├── ProdutoController.java
    ├── ProdutoRequest.java
    └── ProdutoResponse.java
```

Na v0.2, `loja/` e `oferta/` terão a mesma estrutura. Detalhes em `arquitetura.md`.

### O caminho de uma requisição

`POST /produtos` com `{"nome":"  Notebook  "}`:

```
1. Tomcat recebe a requisição na porta 8080
2. Spring MVC escolhe ProdutoController.criar
3. Jackson converte o JSON em ProdutoRequest
4. Bean Validation checa @NotBlank/@Size           ✗ → 400 "Dados inválidos"
5. ProdutoService.criar: trim, ignora id, valida  ✗ → 400
6. ProdutoRepository.save → Hibernate → INSERT INTO produto ...
7. Resposta: 201 Created, Location: /produtos/1, {"id":1,"nome":"Notebook",...}
```

## 5. Componentes

### 5.1 Entidade `Produto`
**Arquivo:** `produto/Produto.java` · **Documento:** `entidade-produto.md`

Classe Java mapeada para a tabela `produto`. Cada objeto corresponde a uma linha.

| Atributo | Tipo Java | Coluna MySQL | Regra |
|---|---|---|---|
| `id` | `Long` | `bigint auto_increment`, chave primária | Gerado pelo banco |
| `nome` | `String` | `varchar(150) not null` | Obrigatório |
| `descricao` | `String` | `varchar(1000)` | Opcional |
| `categoria` | `String` | `varchar(80)` | Opcional |

Anotações principais: `@Entity`, `@Table`, `@Id`, `@GeneratedValue(IDENTITY)`, `@Column`, e do Lombok, `@Getter`, `@Setter` e `@NoArgsConstructor`.

### 5.2 `ProdutoRepository`
**Arquivo:** `produto/ProdutoRepository.java` · **Documento:** `produto-repository.md`

Uma **interface** sem implementação: o Spring Data cria a classe em tempo de execução.
- Herda de `JpaRepository<Produto, Long>`: `save`, `findById`, `findAll`, `existsById`, `deleteById`, `count`, paginação...
- `findByNomeContainingIgnoreCase(String)`: uma **derived query**, cujo SQL é gerado a partir do nome do método:
  ```sql
  select ... from produto where upper(nome) like upper(?)
  ```

### 5.3 `ProdutoService` e `ProdutoNaoEncontradoException`
**Arquivos:** `produto/ProdutoService.java`, `produto/ProdutoNaoEncontradoException.java` · **Documento:** `produto-service.md`

As **regras de negócio**:

| Método | Faz | Pode lançar |
|---|---|---|
| `listarTodos()` | Todos os produtos | - |
| `buscarPorId(id)` | Um produto | `ProdutoNaoEncontradoException` |
| `buscarPorNome(termo)` | Filtra por nome; termo vazio devolve todos | - |
| `criar(produto)` | Limpa os textos, ignora o id, valida e salva | `IllegalArgumentException` |
| `atualizar(id, dados)` | Copia os campos editáveis e valida | ambas |
| `remover(id)` | Apaga | `ProdutoNaoEncontradoException` |

Conceitos: `@Service`, **injeção de dependência pelo construtor**, `@Transactional` (com `readOnly` nas leituras) e **dirty checking**: o `atualizar` não chama `save`, porque o Hibernate detecta a mudança e gera o `UPDATE` sozinho.

### 5.4 `ProdutoController`, `ProdutoRequest` e `ProdutoResponse`
**Arquivos:** `produto/ProdutoController.java`, `ProdutoRequest.java`, `ProdutoResponse.java` · **Documento:** `produto-controller.md`

- **Controller** (`@RestController`, `@RequestMapping("/produtos")`): os 6 endpoints (seção 9). Usa `@PathVariable`, `@RequestParam`, `@RequestBody`, `@Valid` e `ResponseEntity` (para `201` + `Location` e `204`).
- **`ProdutoRequest`** (`record`): o JSON de **entrada**, sem `id`, com `@NotBlank` e `@Size`.
- **`ProdutoResponse`** (`record`): o JSON de **saída**.

Os **DTOs** isolam a API do banco: o cliente não consegue enviar `id`, campos internos nunca vazam e o formato da API só muda quando se decide mudá-lo.

### 5.5 `TratadorDeErros`
**Arquivo:** `erro/TratadorDeErros.java` · **Documento:** `produto-controller.md`, seção 7

`@RestControllerAdvice` que transforma exceções em respostas HTTP no formato **Problem Details** (RFC 9457):

| Exceção | Status | `title` |
|---|---|---|
| `ProdutoNaoEncontradoException` | `404` | Recurso não encontrado |
| `IllegalArgumentException` | `400` | Requisição inválida |
| `MethodArgumentNotValidException` (`@Valid`) | `400` | Dados inválidos, com o mapa `erros` |

Com `spring.mvc.problemdetails.enabled=true`, os erros do próprio Spring (JSON malformado, id não numérico) também usam esse formato.

| Tipo | Arquivos |

| Código de produção | 9 classes Java |

## 6. Infraestrutura: Docker e configuração

**Documento:** `docker-banco-e-testes.md`

### Containers (`docker-compose.yml`)

| Serviço | Imagem | Porta no seu PC | Função |
|---|---|---|---|
| `mysql` | `mysql:8.0` | `3307` | Banco `busca_facil`, dados no volume `mysql_data` |
| `backend` | montada pelo `backend/Dockerfile` | `8080` | A API |

- **Healthcheck** (`mysqladmin ping -h 127.0.0.1`): o Docker verifica a cada 10 s se o MySQL responde. Usar `127.0.0.1`, e não `localhost`, força uma conexão TCP, que só funciona quando o servidor definitivo está no ar.
- **`depends_on: condition: service_healthy`**: o back-end só inicia depois que o MySQL está saudável.

### Imagem do back-end (`backend/Dockerfile`)

- **Multi-stage**: a etapa 1 (Maven + JDK 25) compila; a etapa 2 (só o JRE 25) executa. A imagem final não leva Maven nem código-fonte.
- **`USER 1000`**: a aplicação roda como usuário comum, não como root. Uma falha explorada não dá poderes de administrador no container.

### Configuração (`.env` e `application.properties`)

- **`.env`** (fora do Git; modelo em `.env.example`): `MYSQL_ROOT_PASSWORD`, `DB_USER`, `DB_PASSWORD`. Lido pelo Compose **e** pelo Spring.
- **`${VARIAVEL:padrão}`**: o mesmo arquivo serve aos dois ambientes:

| Onde roda | Banco usado |
|---|---|
| Docker | `mysql:3306`, definido pelo Compose |
| IDE / `mvnw` | `localhost:3307`, o valor padrão |
| Testes | H2 em memória, pelo `application.properties` de teste |

| Propriedade | Valor | Efeito |
|---|---|---|
| `spring.jpa.hibernate.ddl-auto` | `update` | O Hibernate cria e ajusta as tabelas a partir das entidades |
| `spring.jpa.show-sql` | `true` | Mostra no log o SQL executado |
| `spring.jpa.open-in-view` | `false` | Acesso ao banco só dentro das transações do service |
| `spring.mvc.problemdetails.enabled` | `true` | Erros do Spring também em Problem Details |

## 7. Testes

**17 testes, todos passando, nenhum exige Docker.**

| Classe | Tipo | Ferramentas | Testes | O que prova |
|---|---|---|---|---|
| `BackendApplicationTests` | Contexto completo | `@SpringBootTest` + H2 | 1 | A aplicação inteira inicia |
| `ProdutoRepositoryTest` | Fatia JPA | `@DataJpaTest` + H2 | 2 | Salvar, gerar id e buscar por nome |
| `ProdutoServiceTest` | Unitário | Mockito | 6 | Cada regra de negócio |
| `ProdutoServiceIntegracaoTest` | Fatia JPA + service | `@DataJpaTest` + `TestEntityManager` | 1 | O `UPDATE` acontece sem `save` (dirty checking) |
| `ProdutoControllerTest` | Fatia web | `@WebMvcTest` + MockMvc + `@MockitoBean` | 7 | Rotas, status, JSON, validação e erros |

**A estratégia:** muitos testes rápidos e focados (unitários e fatias) e um teste amplo (contexto). Cada tipo prova algo que os outros não conseguem. O teste unitário com mock prova que `save` não é chamado; só o teste com banco prova que o `UPDATE` de fato acontece.

**Por que os testes não precisam do MySQL:** `src/test/resources/application.properties` vem antes no **classpath** durante os testes e substitui o arquivo principal, apontando para o H2.

```bash
cd backend
./mvnw test                                   # todos
./mvnw test -Dtest=ProdutoServiceTest         # uma classe
./mvnw test -Dtest=ProdutoServiceTest#criarRecusaNomeEmBranco   # um método
./mvnw test -Dspring.jpa.show-sql=true        # mostrando o SQL
```

## 8. Como usar: do zero até a primeira requisição

### Pré-requisitos

| Ferramenta | Para quê | Obrigatória? |
|---|---|---|
| **Docker Desktop** | Rodar MySQL + API | Sim |
| **Git** | Baixar o projeto | Sim |
| **JDK 25** | Rodar testes ou a API fora do Docker | Só para desenvolver |

### Passo 1: obter o projeto

```bash
git clone https://github.com/bayma-vh/busca-facil.git
cd busca-facil
git switch feature/v0.1-backend     # ou desenvolvimento, depois do merge
```

### Passo 2: criar o `.env`

```bash
cp .env.example .env
```
Abra o `.env` e preencha as três variáveis, por exemplo `MYSQL_ROOT_PASSWORD=root123`, `DB_USER=busca` e `DB_PASSWORD=busca123`.

### Passo 3: subir tudo

```bash
docker compose up -d --build
```
- `up`: cria e inicia os containers.
- `-d`: em segundo plano, o que devolve o terminal.
- `--build`: monta a imagem do back-end a partir do código.

Acompanhe até aparecer `Started BackendApplication`:
```bash
docker compose logs -f backend      # Ctrl+C sai do log (os containers continuam rodando)
```

### Passo 4: primeira requisição

Abra no navegador: **http://localhost:8080/produtos**. Deve aparecer `[]`, uma lista vazia.

Crie um produto pelo Git Bash:
```bash
curl -i -X POST http://localhost:8080/produtos \
     -H "Content-Type: application/json" \
     -d '{"nome":"Notebook Dell","categoria":"Informatica"}'
```
Resposta esperada: `HTTP/1.1 201`, `Location: http://localhost:8080/produtos/1` e o produto em JSON. Atualize o navegador e ele aparece na lista.

> **Acentos no Windows:** para enviar texto com acento pelo `curl`, salve o JSON num arquivo UTF-8 e use `--data-binary @arquivo.json`. Exemplos para PowerShell estão em `produto-controller.md`, seção 11.

### Passo 5: o dia a dia

| Situação | Comando |
|---|---|
| Ver o estado dos containers | `docker compose ps` |
| Aplicar mudanças no código | `docker compose up -d --build` |
| Parar tudo (os dados ficam guardados) | `docker compose down` |
| Pausar e retomar | `docker compose stop` / `docker compose start` |
| Apagar também os dados ⚠️ | `docker compose down -v` |
| Só o banco, para rodar a API pela IDE | `docker compose up -d mysql` e depois `cd backend && ./mvnw spring-boot:run` |
| Abrir o MySQL pelo terminal | `docker exec -it busca-facil-mysql mysql -u <DB_USER> -p busca_facil` |

**É preciso parar os containers?** Não. Juntos, eles usam cerca de 700 MB de RAM e quase nenhuma CPU parados, e não sobem sozinhos quando o PC reinicia (`restart: no`). Pare quando quiser liberar memória.

## 9. Referência da API

**Base:** `http://localhost:8080` · **Formato:** JSON (UTF-8)

| Método | Rota | Corpo | Sucesso | Erros |
|---|---|---|---|---|
| `GET` | `/produtos` | - | `200` lista | - |
| `GET` | `/produtos?nome={texto}` | - | `200` lista filtrada | - |
| `GET` | `/produtos/{id}` | - | `200` produto | `404`, `400` (id não numérico) |
| `POST` | `/produtos` | `ProdutoRequest` | `201` + `Location` | `400` |
| `PUT` | `/produtos/{id}` | `ProdutoRequest` | `200` produto | `400`, `404` |
| `DELETE` | `/produtos/{id}` | - | `204` sem corpo | `404` |

**Corpo de entrada (`ProdutoRequest`):**
```json
{ "nome": "Notebook Dell", "descricao": "16 GB RAM, SSD 512 GB", "categoria": "Informática" }
```

| Campo | Obrigatório | Máximo |
|---|---|---|
| `nome` | Sim | 150 |
| `descricao` | Não | 1000 |
| `categoria` | Não | 80 |

**Corpo de saída (`ProdutoResponse`):**
```json
{ "id": 1, "nome": "Notebook Dell", "descricao": "16 GB RAM, SSD 512 GB", "categoria": "Informática" }
```

**Erro (Problem Details):**
```json
{
  "title": "Dados inválidos",
  "status": 400,
  "detail": "Um ou mais campos são inválidos.",
  "instance": "/produtos",
  "erros": { "nome": "é obrigatório" }
}
```

**Significado dos status:**

| Status | Significado |
|---|---|
| `200 OK` | Sucesso, com dados no corpo |
| `201 Created` | Criado; o cabeçalho `Location` diz onde |
| `204 No Content` | Sucesso, sem corpo (remoção) |
| `400 Bad Request` | O cliente enviou algo inválido |
| `404 Not Found` | O produto não existe |

Exemplos completos de requisições, com `curl` e PowerShell, estão em `produto-controller.md`, seções 10 e 11.

## 10. Problemas comuns

| Sintoma | Causa | Solução |
|---|---|---|
| `Failed to connect to localhost port 8080` | A API não está rodando | `docker compose up -d` e aguardar `Started BackendApplication` |
| Back-end reinicia ou não sobe; log com `Communications link failure` | O banco não está acessível | `docker compose ps` para ver se o MySQL está `healthy` |
| `Access denied for user` | Senhas do `.env` mudaram depois da criação do volume | `docker compose down -v` e subir de novo (apaga os dados) |
| `Port 3307 (ou 8080) is already allocated` | Outro programa usa a porta | Trocar a porta da esquerda em `ports:` no compose |
| `400` ao enviar acentos; log com `Invalid UTF-8 middle byte` | O terminal não enviou o texto em UTF-8 | Enviar de um arquivo: `--data-binary @arquivo.json` |
| Acentos aparecem como `Ã¡` | O programa leu a resposta como ISO-8859-1 (PowerShell 5.1) | Os dados estão certos; decodificar como UTF-8 |
| `415 Unsupported Media Type` | Faltou `Content-Type: application/json` | Adicionar o cabeçalho |
| `405 Method Not Allowed` | Método errado para a rota (ex.: `PUT /produtos` sem id) | Conferir a tabela da seção 9 |
| Mudança no código não aparece | Imagem antiga | `docker compose up -d --build` |
| Maven: `PKIX path building failed` | Antivírus ou proxy interceptando o HTTPS | Se as dependências já estão baixadas: `./mvnw -o test` (offline) |

## 11. Decisões, limitações e próximos passos

### Decisões tomadas

| Decisão | Motivo |
|---|---|
| Arquitetura em camadas | Cada mudança tem um lugar óbvio; regras reutilizáveis; testes isolados |
| Organização por funcionalidade (`produto/`) | Tudo de uma funcionalidade junto; escala bem com novas entidades |
| DTOs separados da entidade | API estável; impede envio de `id` e vazamento de campos |
| Validação em duas barreiras (DTO + service) | Mensagens claras na entrada HTTP; regras protegidas para qualquer entrada |
| Exceções `RuntimeException` + `@RestControllerAdvice` | Tratamento centralizado; controllers limpos |
| Problem Details (RFC 9457) | Um formato de erro padronizado e documentado |
| Injeção por construtor | Dependências obrigatórias, imutáveis e fáceis de testar |
| H2 nos testes | Testes rápidos, sem infraestrutura |
| Container sem root | Menor impacto se houver uma falha explorada |

### Limitações conhecidas (aceitáveis para a v0.1)

| Limitação | Impacto | Solução futura |
|---|---|---|
| `ddl-auto=update` em vez de migrations | Não remove nem renomeia colunas; mudanças não ficam versionadas | **Flyway** |
| H2 imita o MySQL, mas não é idêntico | Algum SQL específico pode passar no teste e falhar no MySQL | **Testcontainers** |
| Listagem sem paginação | Com milhares de produtos, a resposta fica grande | `Pageable` (`?page=0&size=20`) |
| Sem autenticação | Qualquer um pode alterar dados | Spring Security (v0.3, com Usuario) |
| Sem documentação interativa | A API é descrita só nos `.md` | **springdoc-openapi** (Swagger UI) |
| `PUT` substitui todos os campos | Para mudar um campo é preciso reenviar todos | `PATCH` para atualização parcial |

### Próximos passos

1. **Pull Request** de `feature/v0.1-backend` para `desenvolvimento`, fechando a v0.1.
2. **v0.2: Loja e Oferta.** Novas entidades e os primeiros **relacionamentos** entre tabelas (`@ManyToOne` / `@OneToMany`): uma oferta liga um produto a uma loja, com preço e data de coleta. Isso habilita a **comparação de preços** e o **menor preço**.
3. Melhorias opcionais: paginação, Swagger e Flyway.
